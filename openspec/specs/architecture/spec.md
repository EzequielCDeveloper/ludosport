# Architecture Specification

## Purpose

Define the requirements for ARCHITECTURE.md — the definitive reference for how the Ludosport codebase is structured, how components relate, how data flows, and what conventions govern the build. This document MUST serve as the source of truth for architectural decisions.

## Requirements

### Requirement: App Router Structure

The architecture document MUST describe the App Router layout hierarchy: `layout.tsx` → `page.tsx` → sections, plus error pages (`error.tsx`, `not-found.tsx`) and SEO routes (`sitemap.ts`, `robots.ts`).

#### Scenario: Layout hierarchy is documented

- GIVEN a developer reading ARCHITECTURE.md
- WHEN they look for the page structure
- THEN they see `layout.tsx` wraps all content and `page.tsx` composes sections in order
- AND they see a diagram or tree of the App Router files

### Requirement: Server vs Client Component Boundary

The architecture document MUST include a table of all 17 components, classifying each as Server Component (SC) or Client Component (CC) with the reason for the boundary.

#### Scenario: Component boundary table exists

- GIVEN a developer checking if a component can use hooks
- WHEN they consult the SC/CC table
- THEN they see each component name, its type (SC/CC), and why (e.g., "uses useState", "no hooks — pure render")

### Requirement: Hooks Catalog

The architecture document MUST catalog all 5 hooks with their contracts: input parameters, return values, and which components consume them.

#### Scenario: Hook contracts are documented

- GIVEN a developer reusing or modifying a hook
- WHEN they read the hooks catalog
- THEN they see `useScrollNav`, `useStaggerAnimation`, `useHorizontalCarousel`, `useAccordion`, and `useScrollVisibility`
- AND each entry lists parameters, return type, and consumer components

### Requirement: Dead Code Identification

The architecture document MUST note `useAccordion` and `useScrollVisibility` as dead code, explaining why they are unused and that they are legacy artifacts from the migration.

#### Scenario: Dead code is flagged

- GIVEN a developer considering removing hooks
- WHEN they search for dead code notes
- THEN they find explicit warnings: `useAccordion` (superseded by native `<details>`) and `useScrollVisibility` (replaced by CSS animations) are dead code

### Requirement: Data Flow Diagram

The architecture document MUST include a data flow diagram showing how `lib/constants.ts` feeds into components and JSON-LD.

#### Scenario: Data flow is visualized

- GIVEN a developer tracing how content reaches components
- WHEN they read the data flow section
- THEN they see a diagram (SHOULD use Mermaid) mapping each constant export to its consumers
- AND they see that constants also feed `lib/json-ld.ts` which injects into `layout.tsx`

### Requirement: Component Dependency Diagram (MUST)

The architecture document MUST include a component dependency diagram showing the parent-child tree from `layout.tsx` through `page.tsx` to leaf components, including client component boundaries.

#### Scenario: Component tree is documented

- GIVEN a developer understanding component relationships
- WHEN they examine the dependency diagram
- THEN they see `layout.tsx → page.tsx → [17 components]` with arrows showing which parent renders which child

#### Scenario: Mermaid syntax (SHOULD)

- GIVEN the diagram is implemented
- THEN it SHOULD use Mermaid `graph TD` syntax for GitHub-native rendering
- AND the raw Mermaid source SHOULD be included in the markdown

### Requirement: Styling Strategy

The architecture document MUST document the three-layer styling approach: Tailwind CSS 4 (primary), CSS Modules (`starfield.module.css`), and global CSS (`globals.css` with custom fonts, animations, theme variables).

#### Scenario: Styling layers described

- GIVEN a developer adding new styles
- WHEN they read the styling section
- THEN they understand when to use each layer and the Tailwind v4 CSS-based config (no `tailwind.config.js`)

### Requirement: SEO Setup

The architecture document MUST document the SEO architecture: static `metadata` export in layout, JSON-LD structured data injection, sitemap, robots.txt, and geo/local SEO tags.

#### Scenario: SEO strategy is documented

- GIVEN a developer modifying SEO metadata
- WHEN they read the SEO section
- THEN they learn how metadata is exported from `layout.tsx`, how JSON-LD is generated by `lib/json-ld.ts`, and where sitemap/robots live
